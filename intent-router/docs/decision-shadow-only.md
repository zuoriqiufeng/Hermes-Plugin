# 决定记录：只开 shadow（2026-10-09）

**决定：intent-router 只保留 shadow 观测档，hint / act / 工具面裁剪 / 第三层全部关闭，先采一周真实数据再决定下一步。**

配置上什么都没改——插件默认档位本来就是 `mode: shadow`、其余开关默认 `false`
（见 `plugin.yaml` 的 `config_schema`；`~/.hermes/config.yaml` 里 `intent-router` 没有 settings 覆盖）。
本记录的目的是**把这个决定和它的理由写死**，免得过一阵有人看到这个插件已经装好，误以为它在干活。

## 一、为什么不做「分流」：本场景是 Case B

意图识别有两种被替换的形态，收益完全不同：

| | 原来是什么 | 这个插件的收益 |
|---|---|---|
| Case A | 有一条**独立的分类调用**（每条消息先让模型判意图，如 rag_service 的 `plan_intent`） | 那条调用被本地计算替掉，**每条消息少一次模型往返** —— 实打实的净赚 |
| Case B | 意图识别本来就在**主模型的工具选择**里（i2stream-bkn 的「Tool 是能力暴露，Agent 是编排者」，无独立分类器） | **没有调用可省**，只剩「裁工具面 / 补事实 / 少花一点推理」 |

本系统是 **Case B**。所以：

- 在 Hermes 这一层，「让简单问题不走模型」**做不到**——Hermes 对普通文本消息没有
  受支持的零模型调用回复通道（只有斜杠命令），这一点在设计时已查证；
- 因此这一层正确的定位是**观测 + 补事实**，不是分流。

## 二、两条自我修正（推翻了最初方案里的两个默认认知）

### 1. 「按轮裁剪工具面」与本系统的前缀缓存冲突 → 不用

工具定义（`tools`）**参与请求的前缀缓存**——Hermes 在 tools 数组上挂缓存点
（`gateway`/`agent` 的 bedrock 适配器即 `tools + [cache_point]`）。工具列表一变，
缓存前缀失效，后面整段前缀要按新输入价重算。

而本系统省 token 的主战场**恰恰是缓存**：perf 文档里最大的一笔是缓存重读
25.27M → 8.60M token。也就是说，裁剪省下的是「几个工具 schema」，
代价可能是「整段前缀缓存被打穿」——**净效果大概率是亏的**。
（机制确定；量级可用 watcher 比 `cache_read` 实测，但不必先做。）

**已经在做的正确版本**是静态按面收敛：`known_plugin_toolsets.api_server: [hermes-dag]`
（把 dag 工具从 i2Console 面摘掉）、dag-ops profile 把 cli 面 20 → 6。
静态收敛既省 token、又不动缓存。

→ 将来若要重启 `prune`，**前置条件**：改成**会话内粘滞**（一个会话一个稳定工具面），
或直接用静态面收敛替代它。按轮切换的实现不要开。

### 2. 「提示注入」大概率净亏 → 关

一行 hint 约 40–60 token，每轮都付；而模型本来就能判对「这是错误码问题」。
**花钱告诉模型它已经知道的事**。只有在 shadow 数据证明模型系统性判错时才值得开。

## 三、影子期要采的三个数（决定下一步的唯一依据）

`/intent stats` 看前两个，第三个要查会话记录：

1. **真实流量的 tier1+2 覆盖率** —— 注意：仓库里那份 97.7% 覆盖率跑的是**自造语料**，
   只验证了设计者的假设，不是真实分布的证据；
2. **高置信类的分布** —— 其中多少是「错误码 / 规则号 / 清单」这类**可短路**的，
   多少是「必须模型综合」的症状诊断。这个比例直接决定 i2Agent 那条零 LLM 路值不值得做；
3. **`dag_run` 是否在单点问题上被滥用** —— 现在进图闸门是 prompt 层双轨门控
   （hermes-dag 的工具描述），只有在观测到滥用时，才值得上硬闸。

影子期读数有两个坑已经修掉（否则会被自己的数字骗）：
- 可读日志把反事实渲染成 `动作=hint` → 现在渲染成 `动作=none(本应=hint)`；
- `/intent stats` 把反事实算进「实际触及工具」 → 现在拆成「实际触及工具」与
  「本应触及（shadow 反事实）」两个数。

## 四、停止条件（先说好，避免硬找场景）

若影子数据表明：**覆盖率不高**，或**高置信类集中在「必须模型综合」的症状诊断上**
→ 零 LLM 分流没有东西可短路，**收掉这个方向**，只保留观测（或把观测也挪到 i2Agent）。

## 五、如果继续做，落点在哪

**能实现「零模型调用」的地方是 i2Agent，不是 Hermes。** i2Console 的每条消息必经
i2Agent（`handleChatCompletions` 那个 SSE 代理），它是个服务——可以直接返回，不经任何模型。

```
i2Console → i2Agent
              ├─ 本地分类高置信 且 有确定性答案（错误码/规则号/清单）
              │    → 本地查完直接 SSE 回         ← 零模型 token（Hermes 这层做不到）
              ├─ 高置信 但需要综合（症状诊断）→ 照旧转发 Hermes
              └─ 不确定 → 照旧转发 Hermes
```

代价与要求：
- 逻辑要有一份 Go 实现（归一化 + 词典匹配 + 打分离散门控，约 400 行量级），
  或让 i2Agent 调用同一份 Python 分类器；
- **必须有跨实现一致性回归**：同一份标注语料（现有 63 条 + 现场积累）两边都跑，结果必须一致；
- **taxonomy 不要手写第二份真相**——应从 BKN 图生成（症状清单、诊断类、别名都是图里的现成数据）。
  手写版本的真正风险不是准确率，而是「第二份真相 + 静默腐化」：新增症状类要改三处，没人维护就开始
  悄悄失效（覆盖率下滑、退回模型自己判，不报错）。

## 六、各功能重启的前置条件（速查）

| 功能 | 前置条件 |
|---|---|
| `hint` | shadow 数据证明模型系统性判错（否则净亏） |
| `act`（预取只读工具） | 需要「错误码/规则号」这类高频证据；价值主张是**防模型编错**（i2Stream 私有错误码模型不可能知道），不只是省一轮往返 |
| `prune`（工具面裁剪） | **先解决缓存问题**：改会话级粘滞，或改用静态按面收敛 |
| `tier3`（第三层小模型） | 只在「残差占比高、且第三层结论会改变动作」时才接；默认 `on_ambiguous` 不碰零证据输入 |
| DAG 进图硬闸 | 观测到 `dag_run` 在单点问题上被滥用 |
